Geleneksel vs AykenOS

Geleneksel İşletim Sistemleri

Linux, Windows ve macOS gibi geleneksel işletim sistemleri dosya odaklı (file-centric) bir paradigma kullanır:

  • 300+ syscall: Linux ~400, Windows ~2000 sistem çağrısı
  • Dosya sistemi merkezi: Her şey dosya (device, socket, pipe)
  • Kernel'da politika: Erişim kontrolü, scheduler logic kernel'da
  • POSIX uyumluluğu: Standart API (open, read, write, close)
Geleneksel Dosya İşlemleri (Linux) 
// Linux'ta dosya açma ve okuma
int fd = open("/path/to/file", O_RDONLY);
if (fd < 0) {
    perror("open failed");
    return -1;
}

char buffer[1024];
ssize_t bytes_read = read(fd, buffer, sizeof(buffer));
if (bytes_read < 0) {
    perror("read failed");
    close(fd);
    return -1;
}

close(fd);

// Kullanılan syscall'lar: open(), read(), close()
// Toplam: 3 farklı syscall

AykenOS Yaklaşımı

AykenOS, yürütme odaklı (execution-centric) bir paradigma benimser:

  • 11 syscall: Sadece temel mekanizmalar (1000-1010)
  • Veri odaklı: Dosya yerine veri konteynerları
  • Ring3'te politika: Tüm kararlar userspace'te
  • BCIB execution: Binary Compressed Instruction Bundle
AykenOS Veri Erişimi 
// AykenOS'ta veri konteynerine erişim
execution_plan_t plan = {
    .operation = OP_DATA_QUERY,
    .target = "users",
    .filter = "age > 18",
    .projection = "name, email"
};

// Execution plan'ı gönder
uint64_t exec_id = sys_v2_submit_execution(&plan, sizeof(plan));

// Sonucu bekle
result_t result = sys_v2_wait_result(exec_id);

// Kullanılan syscall'lar: sys_v2_submit_execution(), sys_v2_wait_result()
// Toplam: 2 syscall (ama çok daha güçlü!)

💡 Temel Fark

Geleneksel: "Dosyayı aç, oku, kapat" - Imperative (emir kipi)

AykenOS: "Bu veriyi getir" - Declarative (bildirimsel)

AykenOS'ta "nasıl" yapılacağını değil, "ne" istediğinizi söylersiniz. Sistem en iyi yolu kendisi bulur.

Neden 11 Syscall?

AykenOS'un sadece 11 syscall kullanmasının arkasında derin bir felsefe var:

1. Minimal Kernel Surface

Her syscall, kernel'in "attack surface"ini artırır. Daha az syscall = daha güvenli kernel.

AykenOS 11 Syscall Listesi 
// kernel/include/ayken_abi.h
#define SYS_V2_BASE 1000

#define SYS_V2_MAP_MEMORY       (SYS_V2_BASE + 0)  // 1000: Bellek haritalama
#define SYS_V2_UNMAP_MEMORY     (SYS_V2_BASE + 1)  // 1001: Bellek kaldırma
#define SYS_V2_SWITCH_CONTEXT   (SYS_V2_BASE + 2)  // 1002: Context switch
#define SYS_V2_SUBMIT_EXECUTION (SYS_V2_BASE + 3)  // 1003: BCIB yürütme
#define SYS_V2_WAIT_RESULT      (SYS_V2_BASE + 4)  // 1004: Sonuç bekleme
#define SYS_V2_INTERRUPT_RETURN (SYS_V2_BASE + 5)  // 1005: Interrupt dönüşü
#define SYS_V2_TIME_QUERY       (SYS_V2_BASE + 6)  // 1006: Zaman sorgulama
#define SYS_V2_CAPABILITY_BIND  (SYS_V2_BASE + 7)  // 1007: Yetenek bağlama
#define SYS_V2_CAPABILITY_REVOKE (SYS_V2_BASE + 8) // 1008: Yetenek iptal
#define SYS_V2_EXIT             (SYS_V2_BASE + 9)  // 1009: Süreç sonlandırma
#define SYS_V2_DEBUG_PUTCHAR    (SYS_V2_BASE + 10) // 1010: Debug output

2. Mechanism vs Policy Separation

Bu, AykenOS'un en önemli tasarım prensibidir:

Katman Sorumluluk Örnek
Ring0 (Kernel) Mekanizma - "Nasıl?" Bellek sayfalarını haritalama
Ring3 (Userspace) Politika - "Ne?" Hangi dosyaya erişim izni var?

Ring0 vs Ring3 Ayrımı

Ring0 (Kernel) - Sadece Mekanizma

Ring0: Bellek Haritalama Mekanizması 
// kernel/sys/syscall_v2.c
void* sys_v2_map_memory(void* addr, size_t size, int flags) {
    // Sadece sayfa tablosunu güncelle
    // POLİTİKA KARARI YOK!
    
    // 1. Fiziksel sayfa al
    uint64_t phys_addr = phys_mem_alloc_page();
    if (phys_addr == 0) {
        return (void*)-ENOMEM;  // Bellek yok
    }
    
    // 2. Virtual adrese map et
    uint64_t virt_addr = (uint64_t)addr;
    page_table_entry_t *pte = get_pte(virt_addr);
    
    pte->present = 1;
    pte->writable = (flags & MAP_WRITE) ? 1 : 0;
    pte->user = (flags & MAP_USER) ? 1 : 0;
    pte->physical_addr = phys_addr >> 12;
    
    // 3. TLB'yi flush et
    asm volatile("invlpg (%0)" :: "r"(virt_addr) : "memory");
    
    return addr;
}

// Kernel SADECE "nasıl map edileceğini" bilir
// "Kimin map edebileceğini" BİLMEZ!

Ring3 (Userspace) - Tüm Politika

Ring3: VFS Politika Kararı 
// userspace/libayken/vfs.c
int vfs_open(const char* path, int flags) {
    // 1. Erişim kontrolü (POLİTİKA)
    if (!check_permission(current_user(), path, flags)) {
        return -EACCES;  // İzin yok
    }
    
    // 2. Dosya sistemi seçimi (POLİTİKA)
    filesystem_t* fs = select_filesystem(path);
    if (!fs) {
        return -ENOENT;  // Dosya sistemi bulunamadı
    }
    
    // 3. Dosya boyutunu öğren
    size_t file_size = fs->get_size(path);
    
    // 4. Bellek haritalama (MEKANIZMA - Ring0'a syscall)
    void* mapped = sys_v2_map_memory(
        NULL,                    // Kernel adres seçsin
        file_size,               // Dosya boyutu
        MAP_READ | MAP_USER      // Flags
    );
    
    if (mapped == (void*)-1) {
        return -ENOMEM;
    }
    
    // 5. File descriptor oluştur
    int fd = create_file_descriptor(mapped, file_size, flags);
    
    return fd;
}

// Userspace "kimin ne yapabileceğine" karar verir
// Kernel'e sadece "bunu yap" der

⚠️ Kritik Kural

Ring0'da POLİTİKA KARARI YASAK!

Kernel asla "bu kullanıcı bu dosyayı açabilir mi?" diye sormaz. Bu Ring3'ün işidir.

Bu kural, AykenOS'un constitutional gates ile zorlanır. İhlal = PR AUTO-REJECT!

Pratik Örnek: Dosya Okuma

Geleneksel Sistem (Linux)

Linux: Dosya Okuma 
// Linux'ta dosya okuma
int fd = open("/etc/passwd", O_RDONLY);  // Syscall 1: open()
if (fd < 0) {
    perror("open");
    return -1;
}

struct stat st;
fstat(fd, &st);  // Syscall 2: fstat() - dosya boyutunu öğren

char *buffer = malloc(st.st_size);  // Userspace malloc
read(fd, buffer, st.st_size);  // Syscall 3: read()

close(fd);  // Syscall 4: close()

// Toplam: 4 syscall
// Kernel'de: Erişim kontrolü, dosya sistemi logic, buffer yönetimi

AykenOS

AykenOS: Veri Okuma 
// AykenOS'ta veri okuma
execution_plan_t plan = {
    .operation = OP_DATA_READ,
    .target = "/etc/passwd",
    .flags = READ_ONLY
};

// Ring3 VFS: Erişim kontrolü, dosya sistemi seçimi
int result = vfs_check_and_prepare(&plan);
if (result < 0) {
    return result;  // İzin yok veya dosya yok
}

// Ring0: Sadece bellek haritalama
uint64_t exec_id = sys_v2_submit_execution(&plan, sizeof(plan));  // Syscall 1
result_t data = sys_v2_wait_result(exec_id);  // Syscall 2

// Toplam: 2 syscall
// Kernel'de: Sadece bellek haritalama
// Ring3'te: Erişim kontrolü, dosya sistemi logic

💡 Performans Avantajı

AykenOS daha az syscall kullanır, ama bu sadece sayı değil. Asıl avantaj:

  • Daha az context switch: Ring0↔Ring3 geçişi pahalıdır (~100-200 ns)
  • Daha az kernel kodu: Daha az bug, daha kolay audit
  • Daha esnek: Politika değişikliği için kernel recompile gerekmez

Alıştırma 2: Ring0 vs Ring3 Analizi

Aşağıdaki işlevleri Ring0 (mekanizma) mı Ring3 (politika) mı yapmalı?

  1. Bellek sayfasını fiziksel adrese map etme → Ring0
  2. Kullanıcının dosya erişim iznini kontrol etme → Ring3
  3. CPU context'ini kaydetme/yükleme → Ring0
  4. Hangi process'in önce çalışacağına karar verme → Ring3
  5. Interrupt handler'ı çağırma → Ring0
  6. AI model inference → Ring3
